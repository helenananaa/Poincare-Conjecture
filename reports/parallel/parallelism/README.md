# 实际并行度审计与调度改进

日期：2026-09-19。不是将 jobs 配置当作真实并发，也不声称已经达到全局最优。

旧版本没有明确保存服务启动事件，因此用 capture 时间减去客户端 elapsed 估算区间；平均值覆盖第一次领取到最后集成提交，包含准备、验证与集成等待。不是精确的模型推理占用率。两批峰值均只有 6，平均约 2，不能称为已经充分利用十个工作名额。

## 已修复的串行瓶颈

原调度循环在派发前同步调用 integrate；integrate 还持有与 worktree 创建相同的长锁。现在将单写者集成放到独立线程，模型任务调度不再等待无关的集成构建；worktree 元数据使用单独短锁。前置必须已集成，所选基准必须包含前置提交，数学验收没有放松。

任务优先级加上下游解锁数量决定领取顺序。新增阶段时间记录与只读队列报告；能区分准备、agent 运行、验证以及依赖阻塞。默认工作预算 12，Grok 模型级上限仍为 unlimited；Luna 默认 4、最多 8。可用内存低于 8 GiB 暂停新领取；这些只是资源控制，不表示任意任务图都能有 12 个独立证明。

31 项调度器单元测试通过，包括真实线程/SQLite 下同时启动 12 个合成 worker、集成不阻塞无关任务、失败集成不放行下游、优先级不绕过依赖。合成测试不冒充实际模型调用。

## 本轮真实调用

六个独立 neck 输入准备证明与六个跨主线源码检查并行。现场采样确认本轮自己的六个证明 agent 和六个源码检查 agent 同时 active，共 12 个 Grok；不把其他会话的 agent 算入。六个源码检查报告只用于找任务，不算形式证明。

六个证明全部独立验证并集成。其服务区间峰值 6、同一批区间窗口的平均值 3.458。合并源码检查后的服务区间峰值 12。新旧任务与依赖图不同，不能把这些数值当成同一数学目标的实测速比。

源码检查覆盖 neck、分析估计、典型邻域、手术延拓、有限灭绝、拓扑收尾，返回 18 个候选。所有被列举的 inspected_files 均存在；但尚未逐项完成正式陈述及依赖审查。candidate-queue.json 统一标为 NOT_ENQUEUED_REQUIRES_STATEMENT_AND_DEPENDENCY_REVIEW，而不是立即伪装成 18 个可运行目标。原始报告可能包含错误推断，应以实际源码和之后的核验为准。

## 发现的问题与处理

有一个已验证证明因集成工作区暂时不干净而被拒绝；没有丢弃或绕过检查，之后在锁内将同一交卷正常集成。源码报告最初的 JSON 捕获路径与元数据侧文件同名；已以捕获时 SHA-256 核对停止后的原文件，恢复完全相同的字节，并加入防覆盖测试。不是重造报告，也没有把巡检文本当证明。
